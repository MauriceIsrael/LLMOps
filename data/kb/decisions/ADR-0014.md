# ADR-0014 — Normalized Envelope Response and Unified Server Configuration for MCP

## Context

Third-party MCP client integrations (such as Claude Desktop, Cursor, and automated pipelines) require deterministic error handling, structured status codes, and consistent payload structures across all tools. Without a standard contract, raw exceptions and internal database errors leak into client interfaces, while configuration drift between multiple settings classes creates deployment ambiguities.

## Options considered

**Ad-hoc responses with raw exceptions.**
Returning bare dictionaries on success and raising raw Python exceptions on failure. Quick to code initially, but leaks internal container paths, SQL/Cypher parsing errors, and forces every client to parse arbitrary error messages.

**Normalized response envelope and typed configuration.**
Wrapping every tool response in a standard envelope schema (`status`, `data`, `error`, `code`) with typed helpers (`ok_response`, `error_response`, `not_found_response`, `invalid_argument_response`) and centralizing configuration in a single typed `ServerConfig` model with strict environment parsing.

## Decision

Adopt the normalized envelope schema (`mcp_server/core/envelope.py`) across all MCP endpoints and unify server configuration under `ServerConfig` (`mcp_server/core/config.py`). All tools return envelope dictionaries, and internal errors are mapped to normalized codes.

## Consequences

External MCP clients and web frontends have a predictable contract. Stack traces and database internals are shielded from clients. Adding or modifying tools requires adhering to the envelope protocol.

## Revisit when

An official MCP protocol specification introduces a mandatory native envelope or structured error standard superseding Starlette HTTP/JSON envelopes.

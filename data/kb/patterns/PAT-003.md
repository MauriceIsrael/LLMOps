# PAT-003 — Fallback plan bound to its baseline

## Problem

Pre-validated recovery configurations silently expire when the configuration they assume evolves, and the expiry is discovered during the incident they were prepared for.

## Forces

- Recovery configurations must be prepared in advance to be useful.
- The system they target keeps changing, if only through software upgrades.
- Nobody re-validates a plan spontaneously.

## Solution

Version each plan with an explicit reference to the baseline configuration and the software version it assumes. The validation pipeline blocks, or at minimum raises a blocking alert on, any baseline change that is not accompanied by revalidation of the dependent plans. A periodic report lists plans and their freshness, and the critical subset is exported for the break-glass path by the same pipeline.

## Trade-offs

Adds a constraint to every baseline change. Makes plan debt visible, which is uncomfortable and useful.

## When not to use this

Where recovery is generic and configuration-independent — restoring the last known-good state, for instance — the binding adds ceremony without protection.

## Seen in

One mission-critical mobile network engagement (2026), across transport, container platform and vendor-managed core.

# PAT-011 — MCX SLA latency budget allocation

## Problem

An MCX system has a contractual end-to-end MCPTT access time target (typically < 1,000 ms E2E, < 300 ms in-cell). This budget must be distributed across RAN, core, transport, and the MCX application stack. Without explicit allocation, every team optimises locally, and the integration discovers the budget is overrun only during acceptance testing — where fixing it costs ten times more.

## Forces

- A latency budget assigned to no one is always exceeded.
- Each component owner (RAN, core, transport, MCX application) will negotiate their own share without a system-level referee.
- The budget is asymmetric: the in-cell target (< 300 ms) is tighter than the E2E target (< 1,000 ms) because it excludes transport and MCX server processing.
- Active probes must verify the budget continuously in production, not just at FAT/SAT.

## Solution

Establish a **normalised MCX SLA latency budget** at the start of the technical design phase and maintain it as a first-class architecture artefact throughout the programme.

### Reference SLA targets (3GPP / ETSI MCPTT baseline)

| Metric | Reference Value | Standard Reference |
|---|---|---|
| MCPTT access time (in-cell) | < 300 ms | 3GPP TS 22.179 |
| MCPTT access time (end-to-end) | < 1,000 ms | 3GPP TS 22.179 |
| Mouth-to-ear latency | < 300 ms | ITU-T P.340 |
| MCX late entry time | < 350 ms | 3GPP TS 22.179 |
| MCPTT listening quality | > 4.0 MOS | ITU-T P.800 |
| GIS moving-device update rate | ≤ 30 s or ≤ 200 m | Programme SLA |
| GIS display latency | ≤ 20 s | Programme SLA |

### Budget decomposition per component (illustrative — to be confirmed per engagement)

| Component | Budget allocation | Measurement point |
|---|---|---|
| UE processing + codec | 20–40 ms | UE instrumentation |
| RAN air interface + scheduler | 30–80 ms | RAN KPI export |
| Core network (EPC/5GC bearer setup) | 50–100 ms | Core NF trace |
| Transport (DC-to-DC, if remote MCX) | 5–20 ms | IP probe |
| MCX server processing (floor grant) | 50–100 ms | MCX application trace |
| Margin and jitter | 50 ms | — |
| **Total (in-cell scenario)** | **≤ 300 ms** | Active probe |

For E2E (dispatching position to field device), add the dispatcher leg: typically 100–200 ms additional.

### Enforcement

1. **Architecture gate**: the budget table is reviewed at PDR. Any component allocation exceeding its share requires explicit approval.
2. **Active probes in production**: synthetic MCPTT test calls (SIP test agent) run continuously and alert the NOC when the budget is at risk.
3. **Per-component KPI ownership**: each domain team owns and reports its contribution to the budget at the monthly architecture review.

## Trade-offs

Creates governance overhead during the design phase. Requires instrumentation at each component boundary (which is valuable anyway for operational observability). The budget is an engineering commitment, not a contractual guarantee — actual values depend on platform dimensioning and network topology.

## When not to use this

Do not apply a fixed budget to a system where the SLA is not contractually defined. In that case, use the 3GPP normative values as a design target but do not create governance gates around them.

## Seen in

National MCX programmes (2025–2026) with contractual MCPTT performance acceptance criteria.
